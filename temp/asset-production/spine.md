# Asset Production Spine（跨 Workflow 生产脊柱）

> 归属：`asset-production` 入口（SKILL.md）· 所有 `workflows/<name>.md` 的公共规则基座 · 架构锚 DECISIONS D36 / D43。
>
> **核心原则（D43 原文照录）**：「公共规则集中，生产方法分开，简单资产默认轻量，有新增才加成本。」
>
> **边界（D43）**：Spine 不拥有任何资产语义，只拥有跨 Workflow 的执行规则；Workflow 负责生产方法；Task 负责实例差异。本文件不固化任何具体 Step 集合与 Agent 映射——只定义角色槽与编排骨架规则，具体 Step 集合、执行者映射与验收深度由各 Workflow 按生产方法决定。
>
> **自治条款**：修改本文件 = 生产方法结构变化，须主代理提案 + 用户确认（同步机制升格三级最高档，见 §7）——变更档位写入文件自身，防口头条款漂移。

## 1. Step 编排骨架（规则不是映射）

**角色槽**（六槽；每个 Workflow 的 Step 定义职责 / 输入 / 输出 / 执行角色槽，具体 Step 集合与 Agent 映射由 Workflow 按生产方法决定）：

| 角色槽 | 承担者 |
|---|---|
| research 通道 | 通用子代理（加载 asset-research 技能） |
| 主代理 | 任务拆分 / 派遣 / 协调 / 审查 / 合并 / 最终验收 |
| 几何槽 | procedural-asset-agent |
| 材质槽 | park-shader-agent |
| runtime 槽 | threejs-runtime-agent |
| 独立验证槽 | 通用子代理（按需；不属于上述三专业面的独立验证工作） |

**跨方法恒真规则**：

- Research Gate 先于一切依赖现实对象定义的开发 Step（D26）；纯技术测试 / 抽象效果 / GLB 导入不触发。
- 渲染实现的实质修改主代理不得直接编写，必须由对应专业子代理交付（AGENTS「多 Agent 按 Step 派遣」）。
- 每个独立 Step 默认启动全新的子代理实例（跨 Step 上下文隔离）。
- 并行 Step 文件集不相交；冻结接口在派遣简报中声明——冻结面含**显式签名与隐式接口清单**（uv 帧域 / attribute 语义 / 派生值同源规则如 swatch 推导），不只显式签名。
- **中断即未验证**：跨会话中断的恢复者对交付物全量重验后方可收口；盘点口径 = `git status --porcelain`（含未跟踪文件）+ 目标目录 mtime 扫描 + 定向测试红名单 + 残留进程检查，禁以裸 `git diff` 下「零改动」结论；恢复模式 =「重验 + 补缺」（不推倒重写——两例实测恢复成本约为原派遣 1/3）；恢复简报远程定位一律「假设」措辞、以全量重验为准。
- **配额阻塞期应对**（T030 试行·012.3 回访维持——本任务未触发，待下次触发补证）：阻塞等待期主代理转只读诊断与派遣简报落盘（如校准简报），不空等；「实质修改归专业代理」约束不因阻塞放宽。

## 2. read-set 消费链（D36 第 6 条 / D40）

四环节：**Workflow 定义各 Step 必读集 → 主代理解析为 resolved paths → 派遣简报只传 resolved paths → 专业代理自读正文**（专业代理不自行猜测该不该加载技能）。

- **表格规范（各 Workflow 的 read-set 表须遵守；表本身留各 Workflow，只列该方法真实差异所需）**：三列化 `Path | Section | Mode`；**Section = 读取上限**；不设每 Step 文件数硬上限（无证据基础）。
- **派遣简报形状**：`Step / Task 路径 / Spec 路径@版本 / Workflow 锚点 / Family / Asset 输出路径集 / 冻结接口声明（并行 Step 时）`。
- **回传形状**（T030 试行维持——012.3 两死会话回传全丢未获验证，待下次活会话补证）：子代理回传含 usage 级时长与关键量化计数，结论 / 计数表为主、压缩过程叙述（自报体感时间不可靠——012.2 三次失准实证）。
- **最小上下文读取顺序（D40）**：先读方法索引（方法 / 差异 / 先例选择）→ 需承重数值才定点读 Spec / 先例任务书对应节 → 仍不足报主代理授权扩大。
- **观察钩子**：完成记录记 `index-only / point-read / full-read + reason`（记档非门槛、不设自动触发线）。

## 3. 测试纪律（D40）

- 新测试须对应五者之一——**新增行为 / 新增结构·参数·材质语义 / 新任务新契约 / 新风险 / 公共能力新场景边界首现**；已覆盖公共能力不得因「新增资产」复制测试；测试结构可参考先例、测试内容按新增语义裁定。
- 三门槛判据式口径（定义见 AGENTS.md「工程硬约束」，不在此复制）：代码执行面变化才必须 `npm test`；`check:layers` 与 `typecheck` 恒跑；执行模式（逐子任务 or 末轮统一）按 DECISIONS 当前有效裁定。
- 收尾进程清理：dev server / 浏览器标签 / 后台任务不留跨会话残留；代理清理范围只及自己拉起的进程。

## 4. 视觉验证（抽象三必做 + 疑点触发，D30 最低可信证据原则）

每个资产都必须具备**最低可信证据**，证据深度与资产生产复杂度匹配（复杂度仅是路由判据，具体执行深度由所属 Workflow 定义；复杂资产按 Workflow 执行更深验证，疑点 / 特殊风险 / 新能力按需增加证据）。

**三必做**：

1. **现实 / 目标身份确认**：对照 Reference Spec（或任务书目标定义）的「身份 / 识别特征」出一行结论并记档（含与先例的横向对照读向）。
2. **统一基线验证**：固定机位 + 固定灯光 + 冻结时间的基线帧（**具体参数由 Workflow / 验收 SOP 拥有**）。基线帧按「覆盖资产」而非机械逐资产：复杂资产逐资产一张；轻量批次允许一张覆盖全批的 Contact Sheet（逐资产可辨、固定机位 / 灯光 / 冻结参数），疑点触发再逐资产补图。
3. **问题与契约缺口记档**：有无都记——有 family 归族级验收门，无 family 归任务收口。

**疑点触发**（不作默认）：多机位取证 / 离屏探针 / 动效证据（适用时，形态由 Workflow 定义）/ console 回读 / 表示档间视觉复查（适用时）——由身份判定疑点、任务书疑点清单或开发自检信号触发。

**判读纪律**：console 零错误零警告（通用，含旋转检视）；「表示档间连续」（逐档可辨、无断崖）等档位相关纪律标**适用时**；孤证须多帧仲裁；非像素一帧判读不可作视觉结论，视觉模型输出仅作导航、结论以本地像素量化为准；判读记档以真实工具返回为依据，无返回即未判。

**校准护栏**（D30 第 5 条）：默认一轮、两轮封顶——第二轮仍不达标判**疑似结构性问题**，记契约缺口上收处理，不硬磨参数；终态复拍只拍受影响机位 + 一张基线帧，不整套重拍。

**人工裁定门例外**（D23.7；任务书明确标注才触发，默认不触发）：人工锚点门（首形态定调）/ 形态筛选门（形态向量定稿）——批量出图 → 用户裁定，微调轮次上限同校准护栏；判定过程与轮次记档归任务书完成记录，结果作为后续验收基线。

视觉裁定 = 机器判定为判据，用户异议窗口开放（基线帧 + 取证目录可回溯）；取证落档规范按各 Workflow 指定的验收 SOP。

## 5. 族级验收门七项骨架（带适用性）

横向一致性 / 真实差异成立 / 混合组合场景 / 性能与预算 / **LOD·表示（适用时）** / **契约收口（有 family 时）** / 回归——**不重跑单资产已完成项**（D30 / D31）；family-specific 检查项归各 Epic 定义；骨架即当前升格限度（单族执行经验不足以泛化家族特有项，D40——更多家族真实执行后按 §7 流程教训评估再定）。

## 6. 新 Family 首例流程（D37 六步，任何 Workflow 通用）

1. **Epic 立项**（D33）：先创建族 epic 文件（成员清单 / 族门编号 / 增补规则 / 依赖）；首例任务书挂于其下。
2. **Research Step 照走**：Research Gate → 最小充分调研 → Reference Spec。
3. **家族契约草案创建**（参数化 Step 内执行）：字段全部有真实消费点、一律标注【家族共性候选】（单样本不足以判定家族共性）；数值依据全留资产 config。
4. **首例验收**：按所属 Workflow 定义的首例验收深度执行（D30 最低可信证据原则）——复杂方法走完整首例流程；简单方法走轻量但完整的首例验收；不再统一要求树木级完整 SOP。
5. **完成同步**：先例 / 知识索引不存在则由首例建立（真实消费者触发建库）；流程教训评估照走。
6. **第二例起增量模式**：契约草案经第二个真实消费者消费后**转正定稿**；第二例修订候选字段属草案转正轻量路径，不算契约缺口。

## 7. 同步机制（每资产完成时执行）

- **先例 / 知识索引同步**：所属 Workflow 的索引存在则加行 / 补项，不存在则由本家族首例建立——至少一条资产入口；产生新形态 / 材质 / 结构先例则补对应索引项；不灌水。
- **流程教训评估**（D36 第 11 条）：本资产新发现逐条过**四问筛选器**（当前有效？流程级？跨资产可复用？无更合适归属？）→ **五向分流**：①仅历史事实 → 完成记录；②先例知识 → 索引；③候选流程教训 → 所属 Workflow；④工程契约变化 → docs/procedural-assets 对应规范；⑤执行规则变化 → DECISIONS（并修改所属 Workflow / Spine）。
- **升格三级**：主代理直接记档（历史事实）/ 正常同步（索引）/ **主代理提案 + 用户确认**（生产方法或规范结构变化——重大者独立 grill）；Spine 修改恒属最高档（自治条款）。
- **完成记录收口**（D36 第 10 条）：只记结果、偏离、事故、验证证据与遗留问题，不重复稳定方法论（方法正文在 Spine / Workflow 与 docs）。
- 不含任务排程：预立下一任务由 Epic / TASKS 排程规则决定，不属本节。
